# Project governance

## Principles

- Preserve the distinction between technical implementation and institutional authority.
- Keep normative requirement identifiers stable within a major instrument version.
- Make migrations additive and preserve historical projections.
- Record dissent, conflicts and prohibited inferences.
- Require reproducible tests for changes to schemas, migrations and decision logic.
- Include participant and affected-community expertise in governance when the project enters external pilots.

## Roles

- **Maintainers** merge changes and issue releases.
- **Instrument stewards** review changes affecting normative semantics.
- **Security reviewers** review attack surface and disclosure reports.
- **Domain reviewers** evaluate clinical, regulatory, technical and participant-governance implications.
- **Pilot partners** provide controlled implementation feedback without acquiring authority over unrelated decisions.

## Change classes

- Patch: defects, documentation and non-semantic corrections.
- Minor: additive compatible capabilities and controlled object extensions.
- Major: normative semantic changes, requirement-ID changes or incompatible workspace changes.

No individual reviewer’s comments are represented as UNESCO, regulator, institutional or community consensus without the relevant authority.
