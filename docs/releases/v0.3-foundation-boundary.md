# v0.3 collaborative-assessment foundation boundary

## Status

This document defines the release and authority boundary for the v0.3 collaborative-assessment foundation.

| Layer | State | Meaning |
| --- | --- | --- |
| Package development identity | `0.3.0.dev0` | Development-line identity only. |
| v0.3 foundation engineering | Complete | The bounded collaborative-assessment capabilities described below are implemented and tested. |
| `v0.3.0` software release or tag | Not created by foundation completion | Requires a separate software release action. |
| Canonical observatory `AUTHORIZED` / `PUBLISHED` successor | Not created by foundation completion | Requires an explicit release attestation and, if chosen, a separate publication record. |
| Institutional deployment readiness | Not established | Requires separate institutional controls and applicable external review. |

These states are independent. Evidence for one state must not be used as evidence for another.

## Foundation scope

The v0.3 foundation establishes:

- attributable local review assignments with revocation and supersession lineage;
- disagreement, abstention, dissent, appeal, disposition, and resolution records;
- accepted-proposal application through the versioned assessment-save path;
- metadata-only protected-evidence reference and exchange boundaries;
- deterministic, provenance-linked review and reporting surfaces;
- loss-aware PRIMA v4.2 adaptation and observatory successor/reopening support;
- presentation internationalization and accessibility engineering boundaries;
- byte-reproducible XLSX, DOCX, and PDF publication artifacts;
- a versioned, integrity-addressed, read-only review-state snapshot;
- a proportional default release-attestation profile plus an optional high-assurance governance profile.

Foundation completion does not imply that every external validation activity described by these capabilities has been executed.

## Domain sign-off boundary

The human sign-offs in #7 and #8 accept projection fidelity for the controlled PRIMA adapter and observatory successor/reopening semantics. They do not establish scientific truth, clinical safety or effectiveness, regulatory status, legal authorization, conformance, institutional delegation, or external endorsement.

A domain sign-off is not a software release decision and is not a canonical observatory publication decision.

## Software release boundary

The repository release process is defined in [`../operations/release-process.md`](../operations/release-process.md).

Foundation completion does not create a `v0.3.0` tag, software release, or canonical observatory decision. Software release integrity remains distinct from canonical observatory publication and institutional deployment readiness.

## Canonical observatory release boundary

The proportional default canonical path is:

```text
exact successor candidate + exact products
        |
        v
one six-domain release attestation
        |
        +----> WITHHOLD
        |
        +----> AUTHORIZE
                  |
                  v
          separate publication, if chosen
```

The designated repository authority is `fraware`.

The attestation covers `SECURITY`, `METHODOLOGY`, `DATA_GOVERNANCE`, `ACCESSIBILITY`, `DOMAIN`, and `AFFECTED_COMMUNITY`, binds the exact candidate and product digests, records conditions, and makes an explicit `AUTHORIZE` or `WITHHOLD` decision.

Passing tests, foundation completion, issue ownership, or prior synthetic governance records do not create a real attestation.

The existing v1/v2 scope/opinion/disposition/readiness/release-decision machinery remains available as an optional high-assurance profile. Historical records remain verifiable under the policy version they originally bound.

See [`../architecture/release-attestation.md`](../architecture/release-attestation.md).

## Institutional deployment boundary

The local reference implementation does not acquire production deployment controls through foundation completion. Institutional pilot or production-readiness claims require separate evidence for identity and access control, authenticated transport, encrypted storage, network controls, operational security, independent testing, applicable privacy/clinical/legal review, and named service ownership.

## Fail-closed interpretation rule

Any statement about v0.3 status must identify whether it means:

1. package development identity;
2. foundation engineering completion;
3. software release or tag;
4. canonical observatory authorization/publication; or
5. institutional deployment readiness.

If the intended state is ambiguous, interpret the statement at the narrowest established layer.

## Withheld claims

The v0.3 foundation does not by itself establish:

- a `v0.3.0` software release or tag;
- canonical observatory authorization or publication;
- authenticated institutional reviewer identity or delegation;
- a real default release attestation;
- representative-user accessibility validation;
- translation quality or linguistic equivalence;
- production security or institutional deployment readiness;
- scientific truth, clinical safety or effectiveness, regulatory authorization, legal authorization, or conformance;
- adoption, endorsement, or attribution by any external institution.

These claims remain withheld unless independently satisfied and recorded under their governing processes.
