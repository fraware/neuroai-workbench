# v0.3 collaborative-assessment foundation boundary

## Status

This document defines the release and authority boundary for the v0.3 collaborative-assessment foundation.

| Layer | State | Meaning |
| --- | --- | --- |
| Package development identity | `0.3.0.dev0` | Development-line identity only. |
| v0.3 foundation engineering | Complete when EPIC #6 exit criteria and this boundary are verified on `main` | The bounded collaborative-assessment capabilities described below are implemented and tested. |
| `v0.3.0` software release or tag | Not created by foundation completion | Requires a separate release decision and the repository release process. |
| Canonical observatory `AUTHORIZED` / `PUBLISHED` successor | Not authorized by foundation completion | Remains subject to the separate human-governance and release-authority gates. |
| Institutional deployment readiness | Not established | Requires the controls in the institutional deployment profile and applicable independent review. |

These states are independent. Evidence for one state must not be used as evidence for another.

## Foundation scope

The v0.3 foundation establishes the following bounded capabilities:

- attributable local review assignments, including immutable revocation and supersession lineage;
- attributable disagreement, abstention, dissent, appeal, disposition, and resolution records whose history is preserved;
- accepted proposal application through the ordinary versioned assessment-save path, without silent historical overwrite;
- metadata-only protected-evidence reference and exchange boundaries that keep protected evidence bytes outside ordinary repository and logging paths;
- deterministic, provenance-linked review, decision, evidence-gap, and closure-request reporting;
- loss-aware PRIMA v4.2 adaptation and observatory v1.7 successor/reopening support, with human domain projection-fidelity sign-off recorded in #7 and #8 on 2026-08-15;
- presentation internationalization architecture with deterministic locale resolution and a documented independent linguistic and accessibility review plan;
- deterministic accessibility regression protection for repository-controlled local interfaces and a documented external validation protocol, including representative-user testing as future external evidence;
- byte-reproducible XLSX, DOCX, and PDF publication artifacts under the repository's pinned rendering contract;
- a versioned, integrity-addressed, read-only review-state snapshot suitable as an interchange seam for a later deployment layer.

Foundation completion does not imply that every external validation activity described by these capabilities has been executed. In particular, representative-user accessibility validation and independent linguistic validation remain external evidence unless separately recorded.

## Domain sign-off boundary

The human sign-offs in #7 and #8 accept projection fidelity for the controlled PRIMA adapter and observatory successor/reopening semantics. They do not establish scientific truth, clinical safety or effectiveness, regulatory status, legal authorization, conformance, institutional delegation, or external endorsement.

A domain sign-off is not a software release decision and is not a canonical observatory publication decision.

### Review-state interchange

The review-state snapshot contract verifies stored review-state integrity and event history, emits deterministic versioned state, and identifies that state with a canonical SHA-256 digest. See [`../architecture/review-state-snapshot-contract.md`](../architecture/review-state-snapshot-contract.md).

The digest is a content-integrity identifier. It is not a signature, authenticated identity, non-repudiation record, delegation credential, or authorization decision.

## Presentation review boundary

Internationalization review requirements are defined in [`../architecture/presentation-internationalization.md`](../architecture/presentation-internationalization.md). Accessibility engineering limits and the external validation protocol are defined in [`../architecture/presentation-accessibility.md`](../architecture/presentation-accessibility.md).

The foundation may claim that these review plans exist and that deterministic engineering protections pass. It must not claim translation quality, linguistic equivalence, representative-user validation, assistive-technology interoperability, WCAG conformance, or institutional accessibility readiness without separate evidence.

## Software release boundary

The repository's release process is defined in [`../operations/release-process.md`](../operations/release-process.md). Completion of EPIC #6 does not create a `v0.3.0` tag, release artifact set, release manifest, software bill of materials, attestation, or release authorization.

A future `v0.3.0` software release requires a separate release action that identifies the exact release commit and executes the release process and applicable repository gates. The package development identity `0.3.0.dev0` must not be presented as evidence that such a release exists.

Software release integrity, if later established, remains distinct from canonical observatory publication and institutional deployment readiness.

## Canonical publication and governance boundary

Canonical `AUTHORIZED` and `PUBLISHED` observatory states remain outside this foundation. The deferred-governance boundary is documented in [`../operations/deferred-governance.md`](../operations/deferred-governance.md).

In particular, foundation completion does not substitute for the genuine multi-party operations tracked by #114: independent attributable reviewers, owner dispositions over real review records, a named release-authority decision, and the canonical publication gates. Those roles must remain distinct where the governing policy requires independence.

No local profile identifier, review record, domain sign-off, content digest, test result, or foundation-completion record confers institutional identity or release authority by itself.

## Institutional deployment boundary

The local reference implementation does not acquire production deployment controls through foundation completion. The required institutional controls are listed in [`../architecture/institutional-deployment-profile.md`](../architecture/institutional-deployment-profile.md), including identity and access control, authenticated transport, encrypted storage, network controls, operational security, independent testing, applicable privacy/clinical/legal review, and named service ownership.

An institutional pilot or production-readiness claim requires separate evidence for those controls. Foundation completion is insufficient evidence for that claim.

## Fail-closed interpretation rule

Any statement about v0.3 status must identify which of the following it means:

1. package development identity;
2. foundation engineering completion;
3. software release or tag;
4. canonical observatory authorization/publication; or
5. institutional deployment readiness.

If the intended state is ambiguous, interpret the statement at the narrowest established layer. Do not infer software release, canonical publication, institutional readiness, scientific validity, regulatory status, or external endorsement from foundation completion.

## Withheld claims

The v0.3 foundation does not by itself establish:

- a `v0.3.0` software release or tag;
- canonical observatory authorization or publication;
- authenticated institutional reviewer identity or delegation;
- completed independent multi-party governance;
- representative-user accessibility validation;
- translation quality or linguistic equivalence;
- production security or institutional deployment readiness;
- scientific truth, clinical safety or effectiveness, regulatory authorization, legal authorization, or conformance;
- adoption, endorsement, or attribution by any external institution.

These withheld claims remain withheld unless independently satisfied and recorded under their governing processes.
